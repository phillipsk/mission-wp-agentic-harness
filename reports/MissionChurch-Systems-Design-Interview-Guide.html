1. How to Present This Project in a Job Interview

30-Second Executive Hook

The High-Level Framing

"For my church's website, I originally architected a modern, scale-to-zero Node.js + Firestore + Gemini AI web app on Google Cloud Run to replace a dated WordPress site. When the church board reviewed the MVP and preferred to iterate on WordPress gradually rather than absorb the organizational shock of a full rewrite, I didn't throw away the cloud backend — I pivoted it into an Agentic WordPress Harness. Today, Cloud Run, Cloud Scheduler, and Gmail Pub/Sub watch church bulletins and calendars, use Gemini 2.5 Flash to filter recurring clutter, redact lay members' PII, generate dual flyer graphics, send 1-click HMAC-signed approval emails, and push directly into WordPress Posts and Modern Events Calendar via a custom signed PHP REST bridge — all for ~$0.14/month idle."

Core Senior/Staff Engineering Signals

5. Real-World Incident Post-Mortem: Why 20 Duplicate Emails Fired at 4:01 AM

Observed Live Today (Nov 20, 2026): Inspecting your phillipskevin386@gmail.com inbox and Cloud Run logs revealed 20 duplicate [Mission Church Approval Needed] emails sent in a 31-second burst (04:01:11–04:01:42 AM EST) for 3 real Constant Contact church emails (Christmas Candlelight Service ×9, Christmas Gift Exchange ×6, Friday Prayer Service ×5).
Root Causes Identified in Logs

1. Pub/Sub Concurrency Race Condition

Cloud Run logs showed 29 concurrent POST /api/webhooks/gmail-push requests arriving between 09:00:51Z and 09:01:42Z. Because watchAndPrepareDrafts() executes a read-modify-write cycle (loadStore() → 10–15s Gemini + image generation → sendApprovalEmail() → saveStore()) with no in-memory mutex or atomic Firestore claim, overlapping webhook invocations all read stale processedSourceIds before the first request saved, firing duplicate emails in parallel.

2. Self-Triggering Feedback Loop

Every outgoing [Mission Church Approval Needed] email modifies the Gmail mailbox history, triggering another Gmail Pub/Sub notification! Combined with DEFAULT_GMAIL_QUERY matching broad "missionchurch1@gmail.com" mentions anywhere in a thread/body (without -from:me -subject:"[Mission Church Approval Needed]"), outgoing approval emails can keep waking up the webhook.

Production Remediation Pattern

How to Fix It Permanently (Great Interview Answer!)

  1. Tighten Gmail Search Query: Add in:inbox -from:me -subject:"Mission Church Approval Needed" so the pipeline never inspects its own outgoing approval emails.
  2. Acknowledge Pub/Sub Immediately + Mutex: Return 204 No Content to Pub/Sub immediately (preventing Pub/Sub retry storms if Gemini takes >10s), serialize polling with an in-process pollInFlight lock, and set --max-instances=1.
  3. Atomic Claim-Before-Send (Idempotency Key): Write processed_sources/gmail:{messageId} to Firestore using create / currentDocument.exists=false (optimistic lock) before calling Gemini or sending any email. If the document already exists, skip immediately.
  4. Content/Title Deduplication Window: Deduplicate drafts by normalized (title, startDate) within a 7-day window so duplicate Constant Contact resends don't re-spam the admin.

6. Ten Tough Systems Design Interview Questions & Model Answers

Technical excellence isn't just picking the cleanest framework—it's optimizing for organizational adoption. The church board preferred gradual WordPress improvements to avoid committee churn and member shock. Keeping WordPress as the CMS/presentation layer while turning the Cloud Run service into an invisible AI ingestion & automation harness gave us both: zero disruption for editors and visitors, plus automated calendar/flyer drafting.

Instead of compromising security by disabling host protections or storing raw admin passwords in Cloud Run, I deployed a tiny REST route (/wp-json/mission/v1/publish) via Code Snippets that verifies an HMAC-SHA256 signature (X-Mission-Signature over the raw JSON request body) using constant-time hash_equals against a Secret Manager secret. That same endpoint sideloads base64 images, creates Gutenberg posts, and writes Modern Events Calendar custom tables (wp_mec_events, wp_mec_dates) atomically.

This is a textbook example of at-least-once webhook delivery + non-idempotent read-modify-write race condition. Gmail Pub/Sub delivered concurrent notifications on /api/webhooks/gmail-push while earlier invocations were still awaiting Gemini inference and hadn't written processedSourceIds back to Firestore. The production fix uses three standard patterns: (1) an atomic compare-and-set / create-if-absent idempotency lock in Firestore before side effects (email sending), (2) Pub/Sub fast-ack + single-flight mutex to prevent retry amplification during slow LLM calls, and (3) query exclusion (-from:me) to break self-triggering loops.

Never trust a single LLM prompt for PII compliance. We apply defense-in-depth: (1) structured Gemini prompt rules distinguishing lay members from billed clergy/speakers, (2) a deterministic regex post-processor (sanitizePublicCopy) replacing casual member references (e.g., Brother/Sister X) and non-official email addresses with the church office line while preserving clergy titles/speakers, and (3) a mandatory human-in-the-loop approval email before anything reaches WordPress.

For low-write church traffic (<100 writes/day), a single document gives instant atomic bootstrap reads (1 Firestore read per cold start/sync) and fits easily in the free tier. Revisit triggers: Firestore caps documents at 1 MiB and ~1 write/sec sustained contention—so as processedSourceIds and pendingPosts grow, or to enable atomic per-message idempotency locks, move processedSourceIds into a dedicated collection processed_sources/{sourceId}.

First, captured a full pre-audit REST JSON backup of all 14 pages, 106 posts, 110 events, and taxonomies. Second, audited shortcode usage programmatically across the backup before deactivating (not immediately deleting) 4 zero-usage plugins. Third, implemented the sitewide header, slider, and page fixes inside a single reversible Elementor Custom Code snippet (#8871) instead of mutating 14 Elementor serialized layouts—and verified desktop (1440×900) and mobile (390×844) bounding boxes via automated headless browser checks.

On the first verification pass, screenshots of /give/ and /ministries/ showed cards overlapping the hero slider and an image overlapping the "Why We Serve" heading—even though static CSS had margin-top: 0. Checking bounding boxes immediately after load vs. 2 seconds later proved it was Elementor's entrance animations (animated slideInDown and animated slideInRight) frozen or caught mid-flight! Disabling those animations and resetting transforms eliminated the overlap on initial paint.

Zero secrets live in Git. All API keys, Gmail OAuth refresh tokens, and the WordPress HMAC shared secret live in Google Cloud Secret Manager and are injected at runtime by Cloud Run; WordPress reads its secret server-side without committing it in mission-wp-agentic-harness. Every commit in the portfolio repo is gated by regex secret scanning before pushing.

mission-church-web is the runnable Cloud Run Node.js backend, Firestore store, AI Concierge, Board-reviewed native MVP, and automated GitHub Actions CI/CD deployment. mission-wp-agentic-harness captures the WordPress-facing integration layer: the secret-free PHP HMAC bridge, the sitewide Elementor CSS/JS overhaul engine, synced triage logic, architectural diagrams, and the plugin/draft audit HTML reports.

Everything uses serverless pay-per-use with scale-to-zero: Cloud Run (min-instances=0), Cloud Scheduler (15-min interval, well inside the 3 free jobs), Pub/Sub, and Firestore free tiers cost $0 at church traffic volume. Only 2 Secret Manager secrets beyond the 6 free secrets (~$0.12/mo) and ~155 MB Artifact Registry overage (~$0.02/mo) incur minimal billing.
